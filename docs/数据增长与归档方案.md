# 数据增长与保留策略方案（2026-10-17 · 待评审后实施）

> **状态：方案（未实施）**。本文档回答「上线后用户数据涨起来扛不住怎么办」。
> 原则：**先测量、再清理、后分区**——不为当前规模的假想问题写代码，但把扩展路径和
> 阈值一次写清，规模到线按预案执行。
>
> 关联：`docs/数据库.md`（表结构）、`docs/部署.md`（备份/恢复与运维）、
> `docs/压测报告.md`（承载能力实测）、`docs/任务清单.md`（实施进度）。

---

## 一、目标与非目标

**目标**

1. 让「只增不减」的数据有**明确的保留期与清理机制**（今天完全没有：除会话与订单超时外，其余表只增不减）；
2. 让主表在多年运行后仍保持**列表/统计查询的性能**（归档 + 分区）；
3. 清理与归档**可观测、可回滚**（批量限速、dry-run、审计与指标）。

**非目标（现在不做，写清是为了答辩与防过度设计）**

- 分库分表、读写分离、独立 OLAP —— 单库到千万级完全够用，过早拆会显著抬高复杂度；
- 引入时序数据库（气象/指标）—— 快照量小（见 §二），30 天保留期足够；
- 把日志/消息迁到 Elasticsearch —— 审计日志用 PG 分区 + 索引即可满足本平台查询形态。

## 二、现状盘点（2026-10-17 实测）

`pg_stat_user_tables` + `information_schema` 实查：共 37 个表带时间列，**其中只有 2 个时间列有索引**
（`audit_logs.created_at`、`product_views.viewed_at`）——这是本方案最需要先补的短板：
**没有时间列索引，保留期删除会退化成全表扫描**（大表上就是锁等待与 IO 尖峰）。

| 表 | 增长来源 | 量级（1 万 DAU 估算） | 现有清理 | 时间列 | 时间列索引 |
|---|---|---|---|---|---|
| `ai_messages` | 每次 AI 提问写 2 条 | **~30 万/天 ≈ 1 亿/年** | ❌ 无 | created_at | ❌ 仅 conversation_id |
| `cs_messages` | 客服每轮消息 | ~数万/天 | ❌ 无 | created_at | ❌ 仅 session_id |
| `product_views` | 商品详情浏览（同商品 upsert 不新增） | 与"浏览过的不同商品数"同阶 | ❌ 无 | viewed_at | ✅ |
| `audit_logs` | 审核/运营/客服/订单动作 | 与订单同阶（~1 万/天） | ❌ 无 | created_at | ✅ |
| `sessions` | 登录/刷新（家族轮换） | 每人多次/周 | ✅ 每天 03:00 清理过期 | expires_at | ✅ |
| `device_bindings` | 设备绑定（30 天免密） | 每人 1-3 台 | ❌ 无（表天然小） | last_seen_at | ❌ |
| `orders` / `order_items` | 交易 | ~1 万单/天 | ✅ 超时取消 / 自动确认（**只改状态不删**） | created_at | ❌（有 status/expire_at） |
| `inventory` | 每次库存变动一条流水 | ~2-3 万/天 | ❌ 无 | created_at | ❌ |
| `after_sales` / `after_sale_messages` | 售后 | 远低于订单 | ❌ 无（结单后不再写） | created_at | ❌ |
| `weather_snapshots` | 每天每城市追加 1 天（幂等跳过） | **~8 条/天**（固定量级） | ❌ 无 | snapshot_date | ✅ |
| `payments` | 每单 0-N 个支付单 | 与订单同阶 | ❌ 无（状态已了结的可归档） | created_at | ❌ |
| `notifications` | 支付 / 发货 / 售后每单 1–4 条 | 与订单同阶（~2-4 万/天） | ✅ 365 天保留期（本轮新增） | created_at | ✅ `(user_id, is_read)` |
| `favorites` / `cart_items` | 收藏 / 购物车 | 用户自维护，天然有界 | ❌ 无（可不清理） | created_at | — |
| `files` | 上传（图片压缩后入库，行数=上传次数） | 低 | ❌ 无（对象在 MinIO，需与对象生命周期联动） | created_at | ❌ |
| `users` / `products` / `attractions` 等主数据 | 运营 | 低 | — | — | — |

**结论（风险排序）**

1. **P0 风险：`ai_messages`** —— 唯一的"亿级/年"表，且没有任何清理机制；
2. **P1 风险：`cs_messages` / `audit_logs` / `product_views` / `inventory`** —— 百万级/年，无保留期；
3. **P1 短板：时间列索引缺失** —— 上面任何清理/归档落地前必须先补索引，否则删除即全表扫描；
4. **P2：`orders` 等交易表的"冷数据"** —— 行数不算爆炸，但一年以上历史订单与统计查询会互相拖累（归档即可，不必分区）。

## 三、三层策略与适用阈值

| 层 | 手段 | 适用（阈值参考） | 代价 | 本方案阶段 |
|---|---|---|---|---|
| **L1 保留期清理** | 配置化保留期 + Celery 任务，**批量限速删除** | 单表 < 5000 万行 | 低（纯运维） | P1 |
| **L2 归档（冷热分离）** | 超期数据搬到 `*_archive` 表（或导出文件），主表只留热数据；归档表按年分区 | 单表 5000 万 – 5 亿行，或"历史查询很少" | 中（多一套表与恢复路径） | P3 |
| **L3 时间分区** | PG 原生声明式分区（按月/按天），清理 = `DROP PARTITION`（毫秒、无膨胀） | 单表 > 5 亿行或删除已影响在线性能 | 高（迁移窗口 + 应用侧小改） | P4 |
| **L4 扩展路径** | 只读副本（统计查询分流）、按业务拆库（消息/日志独立库）、冷存储（对象存储归档） | 单库写入/备份成为瓶颈 | 很高 | 仅写文档 |

> 判定口径：**先看 `pg_total_relation_size` 与"清理/查询 P95 是否劣化"**，不要按行数硬套——
> 行数大但访问模式是"最近 N 天"的表（消息/日志/流水）最适合分区；行数不大但被统计查询反复扫的
> 表（订单）更适合归档 + 索引。

## 四、分阶段实施计划（每阶段独立一卡、独立可验收）

### P0 · 观测先行：表增长与清理可见（约 0.5 人日）

- **改动范围**：`backend/scripts/db_size_report.py`（新）——查 `pg_stat_user_tables` 输出
  行数/大小/增长速率（两次采样求差）并按阈值分级；可选：把关键表大小暴露到 `/api/v1/dashboard/metrics`（仅管理员）。
- **验收判据**：`make db-size` 一条命令打印全表行数与大小、标出超过阈值的表；`docs/部署.md` 记录巡检用法。
- **理由**：没有观测就调不了保留期；这张卡也让"上线后怎么办"从猜测变成数据。

### P1 · 保留期清理（约 1 人日）

- **改动范围**：
  - `config.py` 增加保留期配置（**默认值即推荐值**，0 = 关闭）：
    | 配置 | 默认 | 适用表 |
    |---|---|---|
    | `RETENTION_AI_MESSAGES_DAYS` | 365 | `ai_messages`（连同空会话） |
    | `RETENTION_CS_MESSAGES_DAYS` | 365 | `cs_messages` / 已结单 `cs_sessions` |
    | `RETENTION_PRODUCT_VIEWS_DAYS` | 180 | `product_views` |
    | `RETENTION_AUDIT_LOGS_DAYS` | 365 | `audit_logs`（合规下限 6 个月，取 1 年） |
    | `RETENTION_WEATHER_SNAPSHOTS_DAYS` | 30 | `weather_snapshots` |
    | `RETENTION_INVENTORY_DAYS` | 365 | `inventory`（流水对账窗口） |
    | `RETENTION_NOTIFICATIONS_DAYS` | 365 | `notifications`（站内通知，每单 1–4 条） |
  - 迁移：为清理列**补索引**（`ai_messages.created_at`、`cs_messages.created_at`、`inventory.created_at`、
    `device_bindings.last_seen_at`，以及为 P3 归档预置的 `orders.created_at`）——PG 侧用
    `op.get_context().autocommit_block()` 包住 `CREATE INDEX CONCURRENTLY`（避免迁移期锁表；
    alembic 默认在事务里跑，CONCURRENTLY 不能进事务），SQLite 走普通 `create_index`（沿用仓库现有迁移的方言开关）。
  - `backend/app/worker.py`：新增 Beat 任务 `maintenance.purge_expired_data`（每天 04:00，避开 03:00 会话清理），
    逐表按保留期**批量删除**（每批 1000 条、批间 sleep 50ms、单次运行设上限），删除条数打日志并计数。
  - 指标：`metrics.py` 加 `retention_deleted_total{table=...}` 计数器（看趋势判断保留期是否合适）。
  - `scripts/purge_data.py`：**手动 dry-run**（默认只统计不删除，`--yes` 才执行）。
- **验收判据**：造数据脚本灌 N 条 → dry-run 显示应删条数 → 执行后主表行数下降、**窗口内数据不受影响**；
  重复执行幂等；`EXPLAIN` 确认走索引（无 Seq Scan）；`make lint && make test` 绿。
- **风险与对策**：误删 → dry-run 默认、批量限速、删除条数打审计；删错 → 备份/恢复路径已就绪（N16）。

### P2 · 查询体检（可选，约 0.5 人日）

- 对"按时间倒序 + 过滤"的高频查询（订单列表、审计日志、消息）做 `EXPLAIN (ANALYZE, BUFFERS)`
  体检，按需补复合索引（如 `(user_id, created_at)`）；把结论写回 `docs/数据库.md`。
- **验收判据**：三个列表接口的 P95 在 10 万行级数据下不劣化（可用 `scripts/loadtest.py` 压）。

### P3 · 归档（冷热分离，约 1.5 人日，等订单量到线再做）

- **对象**：`orders` / `order_items` / `payments` / `audit_logs`（超过 `ARCHIVE_AFTER_DAYS`，默认 730 天）。
- **做法**：`INSERT INTO orders_archive SELECT ... WHERE created_at < :cutoff` → 校验行数一致 →
  原表 `DELETE` → 记审计；归档表与主表同结构 + `archived_at`；管理端提供"历史订单查询（归档库）"只读入口。
- **验收判据**：归档脚本幂等、行数守恒（源表减少 = 归档表增加）、归档后主表统计查询不包含冷数据但**合计口径正确**。

### P4 · 分区化（约 2 人日，等单表达亿级再做）

- **对象（按优先级）**：`ai_messages`、`audit_logs`、`weather_snapshots`（均按 `created_at` / `snapshot_date` 月分区）。
- **做法**：新建分区父表 + 逐月迁移（`CREATE TABLE ... PARTITION OF`，历史数据用 `INSERT ... SELECT` 分批搬，
  在线切换窗口选低峰）+ Beat 任务每月**预建下月分区**（`maintenance.ensure_partitions`）+ 清理改为
  `DROP TABLE 过期分区`；应用侧只需保证所有查询带时间范围（已满足）。
- **验收判据**：迁移后分区裁剪生效（`EXPLAIN` 只扫命中分区）；`DROP` 过期分区耗时 < 1s 且不阻塞写入；
  备份/恢复脚本兼容分区表（`pg_dump` 原生支持）。
- **前提**：P1 的保留期已跑满一个周期，确认保留期取值合理再上分区（分区后调保留期成本更低）。

## 五、清理任务的技术设计（P1 细节）

1. **批量删除模板**（防长事务与锁等待）：
   ```sql
   DELETE FROM ai_messages
   WHERE id IN (
     SELECT id FROM ai_messages WHERE created_at < now() - interval '365 days'
     LIMIT 1000
   );
   ```
   循环执行至本次上限（默认 5 万条/表/次）或删空；每批 `commit`（避免 WAL 膨胀）。
2. **连带清理**：`ai_messages` 删完若 `ai_conversations` 已无消息且超期 → 一并删（避免空会话列表）；
   客服会话仅在 `closed` 且超期时删。
3. **限速与窗口**：批间 50ms、单表单次上限、任务整体超时保护（沿用 `DB_STATEMENT_TIMEOUT_MS` 语义）；
   04:00 避开业务高峰与 03:00 会话清理。
4. **可观测**：每条表一条 INFO 日志（扫描/删除/耗时）+ 指标 `retention_deleted_total{table}` +
   数据不一致时（删除数 < 应删数）WARN。
5. **审计**：清理属系统动作，`audit_logs.actor_id` 允许空（N1 已放开）；记录 `data.purge` 动作与条数。

## 六、风险与回滚

| 风险 | 触发 | 对策 |
|---|---|---|
| 误删仍在用的数据 | 保留期配错（如 0 天） | 配置下限校验（≥ 30 天或 0=关闭）；dry-run 默认；先跑一周观察 |
| 删除造成主库压力 | 大表全量删除 | 批量 + 限速 + 索引（§P1）；避开高峰；监控 `pg_stat_activity` |
| 清理破坏统计口径 | 概览页/报表读历史 | 统计口径明确为"近 N 天"；归档表提供历史查询 |
| 分区迁移窗口 | P4 的一次性搬迁 | 低峰窗口 + 分批 + 回滚脚本（保留原表至校验通过） |
| 备份体积增长 | 大表进备份 | 归档后主表瘦身；必要时备份拆分为"业务库 + 冷库"两份 |

## 七、答辩/汇报口径（这题怎么答）

> 「用户数据涨起来怎么办」建议分三层回答，并强调我们**已经落地与可实测**的部分：
>
> 1. **当前（单库）**：全站统一分页（上限 100）、时间列索引、保留期清理任务（会话清理已在跑，订单超时/自动确认已在跑）；
> 2. **中等规模**：行为与日志类数据按保留期清理 + 交易冷数据归档到归档表（只读查询入口保留）+ Redis 只放热数据（TTL 与容量上限）；
> 3. **大规模**：消息/日志/快照按时间分区（清理 = DROP PARTITION）、只读副本分担统计查询、必要时按业务拆库；
>
> 并给出**判定阈值**（行数与查询劣化）而不是拍脑袋——避免"为了性能直接把架构上成微服务"的反面教材。

## 八、实施顺序与依赖

```
P0 观测 ──► P1 保留期清理（含补索引）──► P2 查询体检
                     │
                     └─（订单量到线）──► P3 归档 ──► P4 分区 ──► L4 扩展路径（按需）
```

- P0/P1 是**现在就该做**的（与规模无关，属于"该有的运维能力"）；
- P2 可随任何后端改动顺带做；
- P3/P4 **等阈值触发**，触发条件写在 §三，不提前实施。

**预估总工作量**：P0+P1 约 1.5 人日；P2 约 0.5 人日；P3 约 1.5 人日；P4 约 2 人日（按触发再排）。
