## 一、路线原则

1. **先堵真实问题、再做增强**——未被发现的业务漏洞（N1 待支付订单占库存）排在所有增强之前。
2. **契约先行、模块边界、门禁随行**——每卡完成即过 `make lint && make test`（必要时 `make e2e`），接口变化先改契约再改代码。
3. **每批次有可验证的出口判据**——达不到不进入下一批次；验收方式写死在里程碑里（命令 / 浏览器链路）。
4. **等外部输入的挂起项不排产**——真实大模型 / 支付网关资质 / 4.2 拍板不进路线图；唯一例外是 N11（气象源可自主消化，已排入）。

## 三、依赖与并行建议

```
批次0  N18 ────────────┐
批次1  N11 ────────────┼─ 可并行（均独立）
批次2  N1 ─ N2 ─ N3 ─ N4（N4 可选）
                └── N6 待 N2/N3 定稿后固化脚本
批次3  N5 / N7（与批次2 后端卡并行，前端独立）
       N10 ⇢ N9（指标先行，压测更好定位瓶颈）
批次4  N15 / N16 独立；N13 独立；N12 先做载体评估；N14 等拍板
```

- **可全程并行**：N5（控制台测试）、N11、N15 与主线无依赖，时间紧时可多会话并行。
- **硬顺序**：N2 → N3 → N4；N3 完成前不要动 N6 的订单链路脚本（表单字段未定）。
- **先评估后动手**：N12 的 pgvector 载体（现有 postgis 镜像不含 vector 扩展）必须先出结论再排实现。
- **阻塞项**：N14 仅在需求方拍板后启动，未拍板不占用产能。
