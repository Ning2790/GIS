# 开发流程

> 面向 5 人协作团队。照着做即可：从拿到仓库到提交第一个功能。
> 环境配置见 `开发环境.md`；项目结构与约定见 `README.md`；给 AI 的指令见 `AGENTS.md`。

---

## 一、第一次上手（每人只做一次）

### 1. 先把环境对齐
对照 `开发环境.md` 装齐组件，然后自检：

```bash
bash scripts/check-env.sh
```

**只要大版本一致即可**（Python 3.13.x / Node 24.x / pnpm 12.x / uv 0.13.x）。`WARN` 若是补丁号不同可以忽略，`FAIL` 必须装。

### 2. 配置 git 身份
```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

> 如果推送时报代理连接失败，说明 git 配了本地代理但没启动。启动代理工具，或临时绕过：
> `git -c "http.https://github.com.proxy=" push`

### 3. 拉代码并跑起来
```bash
git clone https://github.com/lingbo68/GISxiangmucangku.git
cd GISxiangmucangku

make env          # 安装后端 + 前端依赖
cp .env.example .env

make migrate      # 建表（默认 SQLite，无需 Docker）
make api          # 终端 1：后端 http://127.0.0.1:8000/docs
make web          # 终端 2：游客端 http://localhost:5173
make portal       # 终端 3：统一登录门户 http://localhost:5175（游客 / 商户 / 企业）
```

> 统一登录入口是门户；游客端 / 控制台的 `/login` 现在只做跳转，不再提供登录表单。

**成功的标志**：打开 http://localhost:5173 ，首页显示「后端连接正常」，并且能完成一次游客注册 + 登录。

装好 Docker 后，可切到 PostgreSQL：把 `.env` 里的 `DATABASE_URL` 改成
`postgresql+psycopg://qh:dev@127.0.0.1:5432/qh_platform`（用 `127.0.0.1` 而不是 `localhost`——
Docker 端口只发布在 IPv4，Windows 下 `localhost` 会先解析到 `::1` 导致连接挂起），先 `make infra` 再 `make migrate`。

### 4. 启用提交前格式化
```bash
pip install pre-commit && pre-commit install
```

## 二、日常开发循环

```bash
git checkout main && git pull          # 1. 同步最新
git checkout -b feature/shop-product   # 2. 开分支，命名：feature/<模块>-<简述>

# 3. 写代码（只在自己的模块目录内）

make lint && make test && make build   # 4. 本地自检，必须全绿
make openapi                           # 5. 接口有变动时导出契约并提交

git add -A && git commit -m "feat(shop): 商品列表与详情接口"
git push -u origin feature/shop-product
```

6. 到 GitHub 开 PR → 等 CI 跑绿 → 请至少 1 人 review → 合并 → 删除分支。

**CI 不绿不合并。** 它会自动跑后端 lint + 测试、前端类型检查 + 构建。

## 三、新增一个功能模块的完整步骤

以「特产商城商品列表」为例（模块 `shop`）。**顺序不能反**：模型 → 迁移 → 接口 → 契约 → 前端。

### 后端

**1. 定义模型** `backend/app/modules/shop/models.py`
```python
from sqlalchemy import Integer, Numeric, String
from sqlalchemy.orm import Mapped, mapped_column

from app.db.base import Base


class Product(Base):
    __tablename__ = "products"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    name: Mapped[str] = mapped_column(String(128))
    price: Mapped[float] = mapped_column(Numeric(10, 2))
    stock: Mapped[int] = mapped_column(Integer, default=0)
```

**2. 登记模型** `backend/app/db/models_registry.py`（**漏了这步迁移检测不到新表**）
```python
from app.modules.shop.models import Product  # noqa: F401
```

**3. 生成并执行迁移**
```bash
make migration m="add products table"
make migrate
```

**4. 定义出入参** `modules/shop/schemas.py`，**5. 写数据访问** `repository.py`，
**6. 写业务逻辑** `service.py`，**7. 写路由** `router.py`：
```python
from fastapi import APIRouter

from app.core.response import ok
from app.modules.shop import service

router = APIRouter(prefix="/shop", tags=["shop"])


@router.get("/products", summary="商品列表")
def list_products() -> dict:
    return ok(service.list_products())
```

**8. 挂载路由** `backend/app/api/v1/router.py` —— 已经预先挂好了 10 个模块，新增模块才需要改。

**9. 补测试** `backend/tests/test_shop.py`，然后：

```bash
make test && make lint
make openapi          # 导出契约，一起提交
```

### 前端

**10. 在 `packages/api-client` 补类型与便捷方法**
```ts
export interface Product {
  id: number;
  name: string;
  price: number;
  stock: number;
}

export function listProducts(): Promise<Product[]> {
  return apiGet<Product[]>('/api/v1/shop/products');
}
```

**11. 写页面** —— 游客端放 `apps/tourist/src/pages/`，控制台放 `apps/console/src/`。
组件里**只调用 api-client**，不要直接写 `fetch`。

## 四、用 AI 写代码的正确姿势

团队使用 AI 编程工具，以下几点决定产出能不能用：

1. **先让 AI 读三份文件**：`AGENTS.md`（环境与约定）、`README.md`（模块边界）、
   `docs/api/openapi.json`（接口契约）。不读就会生成风格不一致、拼不起来的代码。
2. **一次只做一个模块、一个文件**。让 AI 一次生成整个后端，边界必然混乱。
3. **明确告诉它边界**：「只改 `modules/shop/` 下的文件，不要动 `core/`、`api/` 和别人的模块」。
4. **生成后必须自己跑** `make lint && make test`。AI 写的代码经常是"看起来对"，跑起来才暴露问题。
5. **关键逻辑人工复核**：支付、权限、库存扣减、认证相关的代码，AI 产出要逐行看。
6. **公共层不要交给 AI 随手改**：`app/core`、`app/api`、`app/db`、`packages/*` 是全队地基，
   改动要单独开 PR 并说明影响面。

## 五、第一周建议任务（按依赖顺序）

**后端先行，前端按契约跟进。** 后端接口一出来就 `make openapi` 推上去，前端即可并行开发。

| 角色 | 第一周任务 |
|---|---|
| 后端 A | `admin`：商户/企业资质审核接口（列出待审核、通过、驳回）；`users`：用户列表 |
| 后端 B | `travel`：`attractions` / `tickets` 表 + 景点列表与详情接口 |
| 后端 C | `shop`：`products` 表 + 商品列表、详情、下单接口（库存先做简单扣减） |
| 前端 A | 游客端：景点列表页 + 商品列表页（按后端契约接） |
| 前端 B | 控制台：商户登录后看到自己的商品管理页（占位数据即可先搭页面） |

每个任务都遵循第三章的步骤，一个 PR 一个功能。

## 六、协作红线

| 红线 | 说明 |
|---|---|
| 不改别人的模块 | 需要别人的数据就调对方 `service`，不要 import 别人的 `repository` / `models` |
| 不改已提交的迁移 | 需要调整就再生成一个新迁移，不要改动历史迁移文件 |
| 不改公共层 | `core` / `api` / `db` / `packages` 改动必须单独 PR + 评审 |
| 契约变更先改契约 | 接口变了先更新 `docs/api/openapi.json`，再改前后端代码 |
| 不提交密钥 | `.env` 绝不提交；仓库里只有 `.env.example` |
| 不绕过锁文件 | 用 `uv add` / `pnpm add` 增减依赖，不要手改锁文件，也不要裸 `pip install` |
| CI 不绿不合并 | 这是"环境真的一致"的唯一客观判据 |

## 七、卡住了怎么办

1. **跑不起来** → 先跑 `bash scripts/check-env.sh` 对齐环境，再核对 `README.md` 的快速开始。
2. **数据库表不对** → 确认模型已登记到 `models_registry.py`，再 `make migration` + `make migrate`。
3. **前后端字段对不上** → 看 `docs/api/openapi.json`，以后端契约为准。
4. **合并冲突** → 只在自己的模块目录内工作，冲突概率极低；真冲突了先找对应模块负责人确认再解。
5. **接口不知道怎么定** → 先在 PR 里讨论契约，定下来再写实现。
