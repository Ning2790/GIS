# 部署指南（P3 部署卡）

> 组成：**Nginx 网关**（HTTPS / 前端静态 / API 反代 / 网关层限流）+ **后端进程**（uvicorn）
> + **基础设施容器**（PostgreSQL / Redis / MinIO，见 `docker-compose.yml`）。
> 本机开发验证与生产部署共用同一套配置，仅 `.env` 不同。

## 架构

```
浏览器 ──HTTPS(443)──► Nginx 网关（容器 qh_nginx，profile: web）
                        ├─ /            → 游客端静态（tourist/dist）
                        ├─ /console/    → 管理端静态（console/dist）
                        ├─ /portal/     → 统一登录门户（portal/dist）
                        └─ /api/  ──►  后端 uvicorn（宿主机 :8000 / 多实例 :8001…）
                                          └─► PostgreSQL / Redis / MinIO（容器内网）
```

- 网关按敏感度分桶限流（登录/注册 2r/s、下单 5r/s、通用 30r/s），与后端应用层限流（`app/core/rate_limit.py`）形成双层防护；
- 后端在受信网关之后时，`.env` 必须设 `TRUST_PROXY_HEADERS=true`（应用层按 `X-Forwarded-For` 识别来源 IP；网关会**覆写**该头丢弃不可信值）；
- 多实例：上游拓扑在 `deploy/nginx/upstream.conf`（宿主机后端）/ `upstream.linux.conf`（容器后端），逐台加 `server` 即可；分发策略是 **least_conn**（依据见 `docs/压测报告.md`「上游分布对照实验」与 §三）。幂等下单 / 库存扣减由数据库约束跨实例兜底（已实测）。

## 本机验证（5 分钟）

```bash
# 1) 基础设施
docker compose up -d                        # postgres / redis / minio
# 2) 证书（自签，365 天）
bash deploy/gen-self-signed-cert.sh
# 3) 前端构建产物（网关挂载 dist）
make build
# 4) 后端
make api                                    # 另开终端；生产为多实例时逐台启动
# 5) 网关（profile=web，默认只绑 127.0.0.1:8080/8443）
make web-gateway
# 6) 验证
curl -k https://127.0.0.1:8443/api/v1/health          # API 反代
curl -kI https://127.0.0.1:8443/                      # 静态（tourist）
curl -kI https://127.0.0.1:8443/portal/               # 统一登录门户
curl -I http://127.0.0.1:8080/                        # 301 → HTTPS
```

浏览器访问 `https://127.0.0.1:8443/`（自签证书需手动信任）。

## 生产部署

1. **配置**：`cp .env.prod.example .env.prod`，逐项替换（密钥用 `openssl rand -hex 32` 生成；数据库/Redis/MinIO 口令同步改 `docker-compose.yml`）。
2. **证书**：替换 `deploy/nginx/certs/` 下的自签证书为正式证书（如 Let's Encrypt；`nginx.conf` 的 80 端口 server 已预留 ACME 校验位置）。
3. **端口与绑定**：`.env` 设 `NGINX_BIND_IP=0.0.0.0`、`NGINX_HTTP_PORT=80`、`NGINX_HTTPS_PORT=443`；**后端与基础设施端口保持仅内网/本机可达**。
4. **启动顺序**：`docker compose up -d` → `make build` → 后端（建议交给进程管理器：systemd / supervisor；多实例时按实例数收紧 `DB_POOL_SIZE`，注意 PG `max_connections` 总量）→ `make web-gateway`。
5. **定时任务**：`uv run celery -A app.worker worker -B -l info`（气象采集 06:00、会话清理 03:00）。

### 数据库故障与超时（N 系列 · 依赖硬化）

- **连接超时**：`DB_CONNECT_TIMEOUT`（默认 3 秒，PostgreSQL）。库不可达或网络黑洞时，
  请求在 **3 秒内**返回 503（此前实测会挂 253 秒，拖住工作线程池与连接池）。
- **语句超时**：`DB_STATEMENT_TIMEOUT_MS`（默认 **10000**，0 = 不设）。连接超时只约束
  「连不上」，管不了「连上了但查询慢」——一条慢查询会长期占住连接与工作线程，把整个
  池拖垮。实测：`SELECT pg_sleep(30)` 在 **10.0s** 被掐断（psycopg `QueryCanceled`）。
  被掐断的请求按「服务繁忙」回 503，但计数走**专属指标** `db_statement_timeout_total`
  （SQLSTATE 57014），与「库不可用 / 池超时」分开——**看到它涨应该去优化慢查询**。
  后台任务（气象采集 / 订单扫描）与 Alembic 迁移**不受影响**：迁移用独立引擎，
  典型查询都是毫秒级；确实需要长语句时把该值调大或设为 0。
  取值须**小于** `DB_POOL_TIMEOUT`（默认 5 秒）——否则请求会先耗尽连接池、被误记成「过载」；
  `0`/负值等于不超时，`libpq` 会把小于 2 的值钳到 2 秒。
- **失败语义**（`app/core/errors.py` 信封 + `app/main.py` 处理器）：
  | 情形 | 响应 | 计数器 |
  |---|---|---|
  | 提交**前**失败（连不上 / 连接中断） | 503 + `Retry-After: 5`（重试安全） | `db_unavailable_total` |
  | 提交**前**等连接超时（并发太猛） | 503 + `Retry-After: 1` | `db_pool_timeout_total` |
  | **提交后**失败（写已落库） | **500 且不带 Retry-After**，文案「请勿重复提交」 | `db_unretryable_failure_total` |
  | 提交结果未知（SQLSTATE 40003） | 同上（可能已提交，不许重试） | `db_unretryable_failure_total` |
  告警口径：前两类是「依赖故障 / 过载」；第三、四类是**最需要人工关注**的——它们意味着
  有写操作已生效但客户端没拿到结果，需要按业务核对而不是重试。
- **排查顺序**：`db_statement_timeout_total` 涨 → 找慢查询（日志里有 SQL 上下文），
  优化或用异步任务承载，而不是调大超时；`db_unavailable_total` 涨 → 看数据库是否在重启 / 网络；只有
  `db_pool_timeout_total` 涨 → **闸门与连接池没对齐**（见下条）；
  `db_unretryable_failure_total` 涨 → 立刻查日志（含 request_id）核对已落库的写操作。
- **上游分发用 `least_conn`**（配置已含）：交替对照实测（500 并发读）请求是均分的、但在途不是
  ——轮询下其中一台会顶满闸门配额成批 503（858/0、582/0），least_conn 下同负载只拒 4/16、0/0，
  放行量相当。2026-10-16 的四组对照实验进一步定位了机制（见 `docs/压测报告.md`
  「上游分布对照实验」）：**拒绝分布取决于「闸门容量 vs 实际在途」**——容量边缘时"在途更高"
  的一台先触容量，轮询下这台是较慢的实例（所以拒绝集中在它）；least_conn 把流量引向空闲的
  快实例，同负载拒绝更少。同时**证伪**了"上游被 nginx 摘除"（`max_fails`）的旧推测：
  门禁返回的是完整 503 响应，不算上游失败，四组实验里摘除次数均为 0。
- **上游拓扑按后端位置切换**（2026-10-16 实现）：拓扑写在 `deploy/nginx/upstream.conf`
  （后端跑宿主机：`host.docker.internal:8000/8001`）与 `deploy/nginx/upstream.linux.conf`
  （后端也在容器：`api:8000`）两个文件里，`nginx.conf` 只 `include /etc/nginx/upstream.conf`，
  compose 用 `NGINX_UPSTREAM_CONF` 选择（`upstream.linux.conf` 已写进 `.env.prod.example`）。
  Linux 生产的 `full + web` 组合按此切换即可（实测：网关日志 `upstream_addr=172.18.0.6:8000`
  即 api 容器，`/api/v1/health`、商品列表、游客端、控制台全部 200）。
- **上游主机名必须只解析 IPv4**（`HOST_GATEWAY`）：Docker Desktop 会给
  `host.docker.internal` 注入一条**不可达的 IPv6**，nginx 轮换地址时该次 connect 直接失败
  （客户端 502）并把该上游摘除 10s——生产网关日志里曾累计 162 次此类报错。
  Windows / macOS 在 `.env` 设 `HOST_GATEWAY=192.168.65.254`（显式 IPv4 会移除 IPv6 记录），
  Linux 保持默认 `host-gateway`（本就是 IPv4）。`docker compose up -d nginx` 重建后生效；
  验证：容器内 `getent hosts host.docker.internal` 只应有一条 IPv4。
- **闸门容量要和连接池对齐**（原则：闸门先拦，别让请求排到池超时）：
  `QUEUE_MAX_TRADE`（默认 50）应 ≤ 连接池能服务的并发数，`QUEUE_MAX_AUTH`（默认 20）
  单独限制 bcrypt 类请求（登录 / 注册 / 刷新——它们秒级占用连接，是池的最大压力源）。
  实测与取值依据见 `docs/压测报告.md`「闸门与连接池容量对齐」；改了 `DB_POOL_SIZE`
  或实例数之后，这两个值要同步复测。
- **语句超时（已实现）**：`DB_STATEMENT_TIMEOUT_MS`（默认 10s，见 `.env.example`）——
  慢查询会被 PG 掐断（SQLSTATE 57014）并按「服务繁忙」回 503，计数走专属指标
  `db_statement_timeout_total`（与"库不可用 / 池超时"分开分诊）。

### 容器化部署（profile full，N15）

不想在宿主机上装 Python/uv 时，后端与定时任务可以整组跑容器：

```bash
cp .env.example .env              # 前置：compose 只读项目根 .env（缺它也能起，但配置会走默认值）
docker compose up -d              # 基础设施（PostgreSQL / Redis / MinIO）
make build                        # 前端构建产物（网关挂载 dist，见上）
make full-up                      # = docker compose --env-file .env --profile full up -d --build
# 生产用独立配置：cp .env.prod.example .env.prod && make full-up ENV_FILE=.env.prod
# 需要网关时再叠加：make web-gateway（profile web 可与 full 组合）
make full-down                    # 只下线容器化后端；基础设施保留
```

**验收清单**（实测均通过）：
```bash
curl -s http://127.0.0.1:8000/api/v1/health                 # 200
curl -s http://127.0.0.1:8000/api/v1/shop/products           # 200（连库）
docker exec qh_worker celery -A app.worker inspect ping       # pong
docker exec qh_worker celery -A app.worker call shop.expire_unpaid_orders   # 任务 succeeded
curl -sk https://127.0.0.1:8443/            # 游客端 200
curl -sk https://127.0.0.1:8443/console/    # 控制台 200
curl -sk https://127.0.0.1:8443/portal/     # 统一登录门户 200
```

**设计要点与注意事项**：

- **开发流程不变**：宿主机 `make api` 照旧；`api` 容器也把 8000 发布到 `127.0.0.1`，
  这样现有网关（upstream 指向 `host.docker.internal:8000`）无需改动即可反代到容器。
  ⚠️ **两者互斥**（同一个 8000 端口），切换前先停掉对方。
- **迁移只在 api 容器跑，且带分布式锁**：入口脚本 `docker-entrypoint.sh` 按
  `RUN_MIGRATIONS`（默认 1）先执行 `python scripts/ensure_postgis.py` +
  `python scripts/run_migrations.py`——后者在 PostgreSQL 上先取会话级 advisory lock
  （带超时），**多副本 / 多机同时启动也只会有一个实例真正迁移**，其余等锁（实测两个容器
  同时对空库迁移：一个执行、一个等待，均 exit 0）；worker 容器显式 `RUN_MIGRATIONS=0`
  且 `depends_on: api(healthy)`，不会在迁移完成前启动定时任务。
- **凭据入口只有一个**：compose 用 `--env-file`（Makefile 的 `ENV_FILE`，默认 `.env`）
  读取；生产把 `.env.prod` 指给它或在 `.env` 里放生产值——别再同时维护 docker-compose.yml
  里的口令（已参数化）。
- **PostGIS 引导**：`postgis/postgis` 镜像只为**默认库**自动建扩展；手动新建的库或外部托管
  PG 会缺扩展（迁移直接失败）。入口已用幂等脚本补建（需要建扩展权限，失败只告警不阻断）。
- **镜像不含 C++ 扩展**：仓库里的 `qh_core.*.pyd` 是 Windows 产物，Linux 镜像里
  `app/core/compute.py` 自动回退 Python 实现（距离 / 选点打分 / 里程功能一致）。
  需要原生性能时在 builder 阶段加编译工具链产出 `.so`，另开一张卡。
- **凭据统一在同一个 env 文件**：`POSTGRES_USER/PASSWORD/DB`、`REDIS_PASSWORD`、
  `MINIO_ROOT_USER/PASSWORD` 同时被基础设施与 api/worker 使用（见 `.env.prod.example`）。
  注意 `POSTGRES_*` 只在**数据库卷首次初始化**时生效，已建库要改口令须进容器 `ALTER USER`。
- **已知边界（当前只针对 Docker Desktop）**：api 容器把 8000 发布到 `127.0.0.1`，
  网关的 upstream 走 `host.docker.internal`——这在 Docker Desktop（Windows / macOS）成立；
  **原生 Linux 上容器访问不到宿主机仅绑回环的端口**，`full + web` 组合会 502。
  → 已实现切换机制：`.env` 里设 `NGINX_UPSTREAM_CONF=./deploy/nginx/upstream.linux.conf`
  （上游用 compose 服务名 `api:8000`），再 `docker compose --profile full --profile web up -d`
  即可；`.env.prod.example` 已默认指向 Linux 变体。宿主机直跑 `make api` 的既有方式不受影响。
- 别用 `docker compose --profile full down` 收工——compose 的 `down` 作用于整个项目，
  会把基础设施一起摘掉；用 `make full-down`（只移除 api/worker）。

### 升级注意（2026-10-16：网关配置拆出 upstream.conf）

`nginx.conf` 现在 `include /etc/nginx/upstream.conf`（上游拓扑按部署形态分文件）。
**拉取本版本后必须重建网关容器**——老的 `qh_nginx` 只挂了 `nginx.conf`，一旦重启
（`docker restart` / 宿主重启 / `docker compose restart`）就会因找不到 include 文件而
`[emerg] open() ... upstream.conf failed` 起来即崩：

```bash
make web-gateway                        # 或 docker compose --env-file .env --profile web up -d nginx
# 生产（后端也在容器）：make web-gateway ENV_FILE=.env.prod（先在 .env.prod 设 NGINX_UPSTREAM_CONF）
```

`docker compose up -d nginx` 会因挂载变化自动重建容器（安全）；**只 restart 不会**。

### 向量检索（N12）

知识问答的检索链路：**向量优先、关键词兜底**（`ai/knowledge.py`）。

- **载体**：向量存在 `ai_knowledge_chunks.embedding`（JSON 列，PostgreSQL 落 JSONB），
  检索在应用层算余弦——本项目知识库只有十几条，零新依赖即可满足；将来换 pgvector
  只需替换检索实现（`app/core/rag.py` 顶部有设计说明）。
- **知识维护**：条目在 `backend/app/modules/ai/knowledge_data.py`（单一事实来源），改完重跑
  `uv run python scripts/seed_knowledge.py`（幂等 upsert，同时按当前嵌入实现重算向量）。
- **嵌入实现**：默认 `EMBEDDING_PROVIDER=mock`——确定性伪嵌入（同义词归一 + 哈希词袋），
  离线可复现，能覆盖「近义表达」这类典型场景（例如「带小孩」↔「亲子出行」），
  **但不是真正的语义模型**。接真实嵌入模型：
  1) 起一个 OpenAI 兼容的嵌入服务（如 vLLM 部署 `Qwen3-Embedding-0.6B`）；
  2) `.env` 设 `EMBEDDING_PROVIDER=openai` + `EMBEDDING_MODEL` / `EMBEDDING_BASE_URL` /
     `EMBEDDING_API_KEY`，并按服务返回调整（维度会自动跟随，无需配置）；
  3) 重跑 `scripts/seed_knowledge.py` 重算全部向量（**换嵌入模型必须重算**，否则维度/语义不一致）；
  4) 抽查一次问答的「参考来源」卡片是否合理。
- **兜底**：表为空、嵌入服务不可用、相似度全部低于 `RAG_MIN_SCORE` 时都会回退关键词检索，
  问答不受影响（测试覆盖了三类回退）。
- **客服**：平台知识命中会并入客服自动应答的提示词，并在回复末尾附一行「参考：…」。

### 接真实支付网关（N13 适配层）

平台不做资金池：`payments` 只记录状态与第三方流水号，收款由第三方完成。当前实现是
`MockGateway`（占位：无支付链接，回调由管理员在控制台模拟），业务代码已经过适配层
（`backend/app/modules/shop/payment_gateway.py`）隔离，接入真实网关的改动面是**确定的**：

1. 实现 `PaymentGateway` 协议（三个方法）：
   - `create_payment`：调第三方「下单」接口，返回 `GatewayPayment(out_trade_no, pay_url)`——
     **`pay_url` 会经 `POST /shop/orders/{id}/pay` 返回给前端**（mock 为 `null`）；
   - `verify_notify`：回调**验签**（支付宝 RSA2 / 微信 APIv3 等）；
   - `parse_notify`：把回调字段映射成 `NormalizedCallback`（如 `trade_status` → `success`）；
2. 在 `shop` 模块新增**持久列 `out_trade_no`**（迁移 + 创建支付单时写入）——回调要可靠
   定位本地单，不能像 mock 那样把 id 编码进单号；
3. 暴露**公网回调端点**（`POST /api/v1/shop/payments/notify` 之类，无鉴权、靠验签），
   内部只调用 `service.handle_gateway_notify(db, headers=..., body=...)`；
   ⚠️ **验签与端点必须同时上线**：mock 网关的 `verify_notify` 恒真，现在开放公网端点等于
   任何人都能标记支付成功，所以本仓库**不提供**无验签的回调端点；
4. 配置：`.env` 设 `PAYMENT_GATEWAY=<你的实现名>`（`get_gateway()` 遇到未注册的名字
   会显式报错，不会静默退回 mock），并把商户号 / 密钥 / 证书放进 `.env`（勿入库）；
5. 回归：`tests/test_payment_gateway.py` 的协议契约用例 + `tests/test_shop.py::test_payment_flow`
   （现有行为零变化是验收判据）。

### 备份与恢复（N16）

```bash
make backup                       # → backups/<时间戳>/：db.dump + minio-data.tar.gz + MANIFEST.txt
make restore d=backups/<时间戳>    # 恢复（会覆盖现有数据；交互确认，演练可加 --yes）
bash scripts/restore.sh backups/<时间戳> --yes --with-minio   # 同时回灌 MinIO 卷
```

- **备份内容**：PostgreSQL 用**容器内 `pg_dump -Fc`**（自定义格式，与运行中的 PG 同版本，
  可用 `pg_restore` 选择性恢复）；MinIO 数据卷用一次性 alpine 容器打包（不依赖 mc）；
  清单记录时间 / 库名 / PG 版本 / 卷名 / git 提交 / 体积，便于核对。
- **恢复步骤**：停容器化后端 → **强制断开其它连接**（宿主机 `make api` 也占连接，会自行重连）
  → drop + create 库（失败自动重试）→ `pg_restore` → `alembic upgrade head`（备份来自旧版本时补齐）
  →（可选）回灌 MinIO 卷（**volume 会被重建，之后需 `docker compose up -d --force-recreate minio`**）。
- **定时建议**：写进 crontab 或 Celery Beat，例如每天 02:30 `bash /path/to/repo/scripts/backup.sh`；
  备份目录定期同步到异机（`rsync` / 对象存储）。恢复演练建议每季度一次。

### 日志与请求追踪（N8）

- **格式**：`ENV != dev` 时输出**单行 JSON**（`ts / level / logger / msg / request_id` + 请求元信息
  `method / path / status / duration_ms`），可直接被 Loki / Filebeat / journald 采集；`ENV=dev`
  保持人眼可读格式。**覆盖范围**：API 进程与 Celery worker（`app.worker` 已装配并把
  `worker_hijack_root_logger` 关掉）；`backend/scripts/*.py` 用 print 输出，不在本口径内。
- **请求 ID**：网关（`deploy/nginx/nginx.conf`）用 nginx 内置 `$request_id` 生成并透传
  `X-Request-ID`；后端**合法则复用**（8–128 位 `[A-Za-z0-9._:-]`，挡住日志注入）、否则自生成，
  并在响应头回带。排障时按该 ID 即可把「网关访问日志 ↔ 后端日志」串起来：
  ```bash
  # 客户端/网关拿到的 ID（响应头或 nginx access log）
  curl -skI https://<域名>/api/v1/shop/products | grep -i x-request-id
  # 后端日志按同一 ID 检索（JSON 行里是字段，直接 grep 即可）
  journalctl -u qh-api | grep <request-id>
  ```
- **慢请求**：耗时 ≥ `SLOW_REQUEST_MS`（默认 500ms，`<= 0` 关闭）记 warning——过载排查先看这些行；
  SSE 流式接口不计入（长连接天然超阈值）。`status / duration_ms` 出现在这些访问日志行上
  （debug 级每次请求一行、warning 级慢请求），uvicorn 自身的 access 行只有 `method / path`。
- **脱敏**：日志（含 JSON 的 `path` 字段与**异常堆栈**）里的手机号掩码为 `138****8000`，
  Bearer 令牌 / `token=` 形态凭据 / JWT / 长随机串替换为 `<token>`（32 位十六进制业务标识如
  `family_id` 不受影响）；当前请求 ID 本身是十六进制但会原样保留（否则无法串联）。

## 图片处理（上传压缩 + 缩略图）

上传图片时服务端会**压缩原图并生成缩略图**（`files` 模块，Pillow）：

- **压缩**：长边超过 `IMAGE_MAX_EDGE`（默认 1600）等比缩小（只缩不放）；JPEG / WebP 按
  `IMAGE_JPEG_QUALITY`（默认 82）重编码，PNG 保持 PNG（`optimize`）。保持原格式族，
  不改扩展名与 `Content-Type`；压缩后不比原图小就**保留原图**。大 JPEG 先按需解码
  （`draft`）到接近目标尺寸，解码内存与耗时降一个量级。
- **缩略图**：长边 `IMAGE_THUMBNAIL_EDGE`（默认 400）；PNG 有透明通道保持 PNG，
  否则转 JPEG（列表场景体积差一个量级）。列表页读 `?variant=thumb`，详情页读原图。
- **元数据**：重编码时按 EXIF 方向固化像素并**丢弃元数据**（EXIF / GPS 不外泄）。
- **不处理的输入**（原样入库，永不阻断上传）：非图片、伪造头 / 损坏图、**动图**
  （动画 WebP / APNG——重编码只会留第一帧，等于静默销毁动画）、超过 4000 万像素的大图
  （解码内存防线）。16 位整数 / 浮点灰度图会归一为 8 位灰度后照常处理（Pillow 已废弃
  PNG 存 16 位）。
- **两种缺失都回退原图**：没有缩略图（上面几类输入 / 存量文件）与缩略图对象丢失
  （人工清理、快照不一致）——`?variant=thumb` 都返回原图而不是 404；`FilePublic.thumbnail_url`
  只在**真的生成了缩略图**时才有值，前端按空值回退原图。
- **配置**：`IMAGE_MAX_EDGE=0` 关压缩、`IMAGE_THUMBNAIL_EDGE=0` 关缩略图（只影响新上传）。
- **对象一致性**：写对象失败 / 入库 flush 失败会补偿删除已上传对象；仅**提交结果不确定**
  （如提交超时，可能服务端已提交）时保留对象并记 `文件入库提交失败，已保留对象待对账`
  error 日志（含两个对象键），宁可留可清理的孤儿对象，也不让已入库记录指向被删对象。

存量图片（该功能上线前上传的）补缩略图（幂等，可反复运行；**不改动原图对象、不覆盖已有
`original_size`**；数据级不一致只报告不返回失败码）：

```bash
make thumbs            # = cd backend && uv run python scripts/make_thumbnails.py
```

实测（本机 3000×2250 JPEG 6.6 MB）：上传 → 原图 489 KB（-92.8%，1600×1200）、
缩略图 9.5 KB（1.9%，400×300）；动画 WebP 原样入库（字节一致、仍是动图、无缩略图地址）；
16 位灰度 PNG 6386 → 3451 字节并生成 400×300 缩略图；删掉缩略图对象后 `?variant=thumb`
回退原图 200；演示库 7 张存量商品图回填后列表页全部走 400px 缩略图。

## 搜索热词与 PWA 离线壳（增强项）

**搜索热词**（`core/hot_search.py`）：Redis 有序集合 `shop:hot_search` 累计搜索次数，
**整键 7 天过期**（近似窗口：任意一次搜索都会刷新整键 TTL，单个词的分数不单独衰减）。
未配置 / 不可用 Redis 时全部静默降级（记录不做、`GET /api/v1/shop/hot-keywords` 返回空表），
搜索本身不受影响；连接失败会进入 30 秒熔断，避免 Redis 故障时每次搜索都等超时。

计数口径与防滥用：

- 每次商品**列表请求**计一次（含翻页与命中列表缓存）——热词是"被搜过"的近似统计；
- 单字 / 超长（>24 字）/ 无实义字符（纯控制字符、零宽字符、纯标点）的关键词不收录；
- 集合成员上限 `MAX_MEMBERS=500`，每 50 次记录按热度裁一次尾部——记录发生在**公开无鉴权**
  的搜索接口上，而 Redis 与限流计数、库存预扣闸门共用实例，必须有上限。

前端在商城搜索框下展示热词胶囊，点击即搜。

**PWA 离线壳**（游客端）：

- `frontend/apps/tourist/public/{manifest.webmanifest,sw.js,icon-*.png}`；Service Worker
  **只在生产构建注册**（`import.meta.env.PROD`），开发期不装（否则会拦 HMR）。
- 策略：预缓存首页壳（`/`、manifest、图标，逐个 `add`——单个文件缺失不会让整个 SW 装不上）；
  导航请求网络优先、离线且**属于游客端路由**时回退首页壳（`/console/` 等其它前端不接管，
  避免离线访问控制台却显示游客端首页）；运行时缓存**白名单**（`/assets/`、壳文件、图标），
  `/console/` 产物不进游客端缓存；`activate` 只清理 `qh-tourist-` 前缀的旧缓存
  （Cache Storage 是 origin 级，不能误删他方缓存）；**`/api/` 与跨域请求完全不拦截**——
  离线时页面能打开、数据部分按各页面的失败态优雅降级（不缓接口，避免把过期库存 / 价格
  当成实时数据），页面顶部同时显示**「当前离线」横幅**（`App.vue`）说明看到的是缓存。
- 更新：改 `sw.js` 里的 `CACHE` 版本号即发布新壳；nginx 对 `sw.js` 与
  `manifest.webmanifest` 配 `Cache-Control: no-cache`，保证浏览器总能拿到最新壳
  （见 `deploy/nginx/nginx.conf`）。
- 实测：本地起生产构建（`pnpm --filter @tourist... preview`），确认 SW 已接管
  （`navigator.serviceWorker.controller` 为真、缓存里含首页与两个图标）；**停掉静态服务**
  后刷新，页面仍完整渲染（导航与四大入口可见），状态行显示「后端未连接」——即离线壳生效。

## 数据保留期与清理（维护卡 P0+P1）

行为 / 日志类数据**只增不减**（AI 消息、客服消息、浏览历史、审计日志、气象快照、库存流水），
按保留期自动清理。方案与阈值判定见 `docs/数据增长与归档方案.md`。

| 配置 | 默认 | 适用表 |
|---|---|---|
| `RETENTION_AI_MESSAGES_DAYS` | 365 | `ai_messages`（连带清理无消息的旧会话） |
| `RETENTION_CS_MESSAGES_DAYS` | 365 | `cs_messages`（仅**已结单**会话）与无消息的已结单会话 |
| `RETENTION_PRODUCT_VIEWS_DAYS` | 180 | `product_views`（浏览历史） |
| `RETENTION_AUDIT_LOGS_DAYS` | 365 | `audit_logs`（合规下限 6 个月） |
| `RETENTION_WEATHER_SNAPSHOTS_DAYS` | 30 | `weather_snapshots` |
| `RETENTION_INVENTORY_DAYS` | 365 | `inventory`（对账窗口之外；库存余额在 `products.stock`） |
| `RETENTION_BATCH_SIZE` / `RETENTION_MAX_PER_RUN` | 1000 / 50000 | 每批条数 / 单表单次上限（限速，超出留到下次） |

- **自动**：Celery Beat 每天 **04:00**（`maintenance.purge_expired_data`，避开 03:00 会话清理）；
  删除按批提交（避免长事务与 WAL 膨胀），每表记录 `retention_deleted_total{table}` 指标与日志；
- **手动**：`make purge-data` 默认**演练**（只统计将删除条数），`make purge-data ARGS=--yes` 才执行；
- **观测**：`make db-size`（全表行数 / 大小 / 超阈值标红）——判定是否该收紧保留期或上分区；
- **索引**：迁移 `0df094c78e71` 为 5 个时间列补了索引（PG 用 `CREATE INDEX CONCURRENTLY`，不锁表）
  ——**没有索引时保留期删除会退化为全表扫描**，这也是本功能的前置条件；
- **`0` = 关闭**该类清理（演练环境常用）。

## 常见问题

- **502 Bad Gateway**：后端未启动或端口不符。宿主机拓扑看 `upstream.conf`（指向 8000/8001）；
  容器拓扑看 `upstream.linux.conf`（`api:8000`）——Linux 上误用宿主机拓扑会**全量 502**
  （容器访问不到宿主机仅绑回环的端口），见「上游拓扑」一节。
- **网关容器起来就崩（`[emerg] host not found in upstream "api:8000"`）**：选了 Linux 拓扑但
  api 容器还没起 / 不同网络；nginx 启动时静态解析上游名字，先起后端再起网关即可。
- **经网关后 IP 限流"失效"**：忘了设 `TRUST_PROXY_HEADERS=true`——此时所有请求被识别为网关容器 IP，IP 维度限流退化为全局共享。
- **SSE 不流式（一次性返回）**：API 反代需 `proxy_buffering off`（本仓库配置已含；自定义网关时注意）。
- **上传 413**：网关 `client_max_body_size` 与后端 `FILE_MAX_MB` 需匹配（默认 12m / 10MB）。
- **Git Bash 生成证书报 `-subj` 路径错误**：脚本已内置 `MSYS_NO_PATHCONV=1`（Git Bash 路径转换坑），直接用脚本即可。
