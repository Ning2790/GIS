## 二、A 类：已实测复现

### A1 [高] 并发同幂等键下单 → HTTP 500（shop）

- **端点**：`POST /api/v1/shop/orders`、`POST /api/v1/shop/cart/checkout`（同源代码路径）
- **实测**：4 个并发请求携带同一 `idem_key` → `HTTP [200, 200, 500, 500]`；另一次 2 并发 → 含 500。
  事后顺序重放返回同一订单（200），说明幂等本身在串行路径是好的。
- **机制**：
  - `repository.create_order` 内 `db.add(order)` 后**显式 `db.flush()`**（`backend/app/modules/shop/repository.py:78-82`），INSERT 在这一步就执行；
  - service 层的 `try / except IntegrityError` **只包住 `db.commit()`**（`backend/app/modules/shop/service.py:247-255`，checkout 同形：`371-379`）；
  - 并发重放请求的 INSERT 在 flush 点抛 `UniqueViolation (uq_orders_user_idem_key)`，**抛错点位于 try 之外**，重放（查到已有订单并返回）逻辑根本不执行 → 冒泡到 `main.py` 兜底异常处理器 → 500 信封。
- **证据**：uvicorn 日志两份 traceback —— 上个会话（user 36, `audit-91873851`）与本次（user 37, `race-9679d3f6…`），异常均为
  `duplicate key value violates unique constraint "uq_orders_user_idem_key"`。
- **影响**：幂等契约在并发下退化为 500；客户端可能把"下单失败"当真并重试或触发下游补偿。订单不重复（DB 约束兜底），但错误响应本身即缺陷；该失败路径还触发 A4 的预扣泄漏。
- **复现**：注册游客 → 商户商品库存充足 → 4 线程 barrier 同步 `POST /shop/orders`（同 `idem_key`），观察状态码。

### A2 [高] 并发发起匹配 → HTTP 500（b2b）

- **端点**：`POST /api/v1/b2b/demands/{id}/match`
- **实测**：4 个并发请求 → `HTTP [200, 500, 500, 500]`；DB 最终 2 行匹配（无重复），事后串行再匹配正常。
- **机制**：`replace_matches` 先 DELETE 后 INSERT（同一事务），**没有任何 IntegrityError 处理**（`backend/app/modules/b2b/repository.py:112-117`）。并发时先提交方插入成功，后到者的 INSERT 撞唯一约束 `uq_b2b_match`（`b2b/models.py:76`）→ `db.commit()` 抛错 → 500。
- **影响**：匹配是"全量替换"的幂等语义，用户重复点击 / 前端重试即触发；3/4 失败率说明窗口很宽。
- **复现**：enterprise 用户发布 1 需求 + 2 供给（同品类）→ 4 线程同步 `POST .../match`。

### A3 [中] Redis 库存闸门 TTL 保护失效（shop）

- **实测**：`GET shop:stock:3` → 值与 DB 一致（97），但 **`TTL` = -1（永不过期）**。
- **机制**：`_redis_reserve` 首次建键时设置了 3600s TTL（`shop/service.py:74-76`），但每次成功下单后的 `_redis_sync` 用**不带过期的 `client.set()`** 覆盖（`shop/service.py:96-103`）→ TTL 被清除。代码注释宣称的"到期后从数据库重新同步，避免 Redis 与数据库长期漂移"（`shop/service.py:37-38`）实际失效。
- **影响**：一旦发生漂移（见 A4），会一直残留到下一次成功下单或 Redis 重启；闸门可能持续误拒。
- **修复方向**：`_redis_sync` 改用 `setex` / `set(..., ex=STOCK_KEY_TTL_SECONDS)`。

### A4 [中] 幂等竞态失败路径的 Redis 预扣不回补（shop）

- **机制（时序推演，未单独实测）**：
  T2 通过幂等检查（当时无损）→ T1 全流程完成（commit + `_sync_all` 用 DB 权威值重置 Redis）→ T2 执行 Redis 预扣（-q）→ T2 的 flush 撞唯一约束 → 500；T2 的 session rollback 只回滚 DB 扣减，**Redis 预扣无任何回补**（`_compensate_all` 位于 `db.commit()` 的 except 分支内，flush 点抛错的请求到不了那里）。
- **影响**：Redis 库存比 DB **偏少**（保守方向，不会超卖），但会拒绝本可成功的下单；叠加 A3（无 TTL）后漂移不自愈。
- **修复方向**：把兜底补偿放到与 A1 相同的修复里（try 前移 / savepoint + 统一 except：rollback → 重放查询 → 未命中再 `_compensate_all`）。

### A5 [中] 并发加入购物车 → 500 + 数量丢失更新（shop）

- **端点**：`POST /api/v1/shop/cart/items`
- **实测**：4 个并发（同用户同商品每次 +1）→ `HTTP [200, 200, 200, 500]`，且最终 `quantity = 2`（期望 4——其中一次被吞）。
- **机制**：
  - check-then-insert：先查再插（`shop/service.py:272-287`），插入走 `repository.add_cart_item` 的 `db.flush()`（`shop/repository.py:131-135`），并发插入撞 `uq_cart_items_user_product`（`shop/models.py:117`）→ 未捕获 → 500；
  - 合并路径 `existing.quantity = merged` 是 read-modify-write（无锁），并发下两个请求都基于旧值加一 → 丢失更新。
- **影响**：双击"加入购物车"即可触发 500 与数量少算。购物车属低价值数据，故为中危。

## 三、B 类：代码路径确认（未实测，机制清晰）

### B1 [中] gear 采集 / 建议缓存的并发冲突

- `collect_snapshots` 对每个 (city, date) 先查后插（`gear/service.py:85-103`），`create_snapshot` 内 `db.flush()`（`gear/repository.py:37-41`），唯一约束 `uq_weather_city_date`（`gear/models.py:33`）在并发时于 flush 点抛错，**无捕获** → 整个批次回滚。触发场景：手动 `scripts/collect_weather.py` 与 Celery beat 同时跑、或 worker 重入。幂等重跑可自愈，但产生任务失败与错误日志。
- `get_advice` 的推荐缓存同形（`gear/service.py:139-167`）；`GearRecommendation.snapshot_id` 唯一（`gear/models.py:42`），并发首访同一快照 → 500。

### B2 [中] travel 停靠点并发替换 → 静默重复

- `replace_stops` 先删后插（`travel/repository.py:97-102`），**itinerary_stops 无 (itinerary_id, day, position) 唯一约束**（`travel/models.py:73-86`）。并发 PUT（双击保存 / 双标签页）时两个事务互看不到对方插入 → 两套停靠点都落库（如 3+2=5 行），无报错、无 500，数据静默损坏且用户可见（详情页重复条目）。
- 与 A1/A2 同源（delete-then-insert 或 check-then-insert 并发窗口），但此处**没有 DB 最后防线**，后果比 500 更难发现。
- 修复方向：加唯一约束 + 冲突重试，或在替换前对该行程行 `SELECT … FOR UPDATE` 串行化。

### B3 [低-中] cpp_core Haversine 对跖点浮点域不一致

- 两实现均直接 `asin(sqrt(a))`（`cpp_core/src/recommend.cpp:22`、`backend/app/core/compute.py:29`）。理论上 `a ≤ 1`，但浮点误差在**对跖点附近**可使 `a` 略大于 1：
  - C++：`std::asin` 返回 **NaN**（静默；NaN 随后进入排序 key，比较全 False，顺序未定义）；
  - Python 回退：`math.asin` 抛 `ValueError: math domain error` → **HTTP 500**。
- 公开端点 `GET /travel/attractions?near=lng,lat` 可构造触发（需把坐标逼近与某景点对跖的浮点边缘），且同一请求在"有编译扩展 / 无扩展"环境行为不同——违反 compute.py 文档"两套实现必须保持一致"的承诺。
- 修复方向：两侧都加 `a = min(a, 1.0)`，并补一条对跖点用例进 `tests/test_compute.py`。

### B4 [低] ai `ask` 跨 4 个独立事务

- `ask` 一次调用实际提交 4 次：`create_conversation`（`ai/repository.py:12-16` 内 commit）、`add_message(user)`（`ai/repository.py:28-32` 内 commit）、`add_message(assistant)`、最后 service 再 commit（`ai/service.py:157-179`）。非原子：中途失败/进程崩溃留下"有问无答"或"有会话无消息"的半成品；LLM 失败有兜底（设计如此）。
- 该问题的根因是仓库分层事务约定不一致：shop repository 明确"只 flush 不 commit、事务由 service 控制"（`shop/repository.py:5`），而 ai / b2b / travel 的 repository 内部 commit。建议统一（B4 随约定统一自然修复）。

### B5 [低] ai SSE 端点语义

- `GET /ai/ask/stream` 带写副作用（建会话、落两条消息，`ai/router.py:32-45`）——GET 可被预取 / 代理 / 缓存触发非预期写；建议改 POST（前端 EventSource 可用 fetch + ReadableStream 兼容）。
- 流式为"先完整生成再按 24 字符分块"（`ai/service.py:186-197`），注释已声明为 mock 取舍，接真实流式模型时替换——不算缺陷，仅备案。

9. **B5**（`ai/router.py` + `tests/test_ai.py`）：SSE 端点改为 `POST /ai/ask/stream`，请求体复用 `AiAskRequest`；前端当前未接入该端点（api-client 无调用），无需适配。

**复核新增修复（2 处，同类模式扫尾）**：

1. **users 注册并发冲突未捕获**（同类模式第 4 处漏网）：`register` 先查后插，`repository.create` 在 commit 点抛 `IntegrityError` 且未捕获——并发同手机号注册 → 500。修复：捕获后 rollback 并返回 409「该手机号已注册」。实测 4 并发同手机号：**1×200 + 3×409，无 500**。
2. **travel `replace_stops` 并发删除窗口加固**：行程在校验后、加锁前被并发删除时，锁查询拿不到行、后续插入撞外键 → 500。修复：锁查询取 `first()`，无行时返回 False，service 转 404。实测「删除后替换」→ 404「行程不存在」。

**复核修正（1 处，B3 定性更正）**：Haversine 对跖点边界**不是防御性修复，而是真实可触发**——存在 2 ULP 越界坐标对 `(65.23655595123734, 155.21888059145596) ↔ (-65.2365559507342, -24.78111940793167)`：旧实现下 Python 回退 `math.asin` 抛 `ValueError`（公开端点 500），同点 C++ `std::asin` 静默得 NaN。回归用例已从 1 ULP 对（旧代码也不触发、防回归力弱）更换为该触发对；修复后 C++ 与 Python 均返回精确 πR。此前"无法构造触发输入"的判断有误——随机搜索 120M 样本未命中，但精确构造可达。

**复核改进（1 处，把已知残余收敛掉）：Redis 闸门补偿改为「按数据库权威值对齐」**。
- 原实现：失败请求对预扣做 `INCRBY` 加回——在并发下与成功请求的同步 `SET` 相互交错，产生可正可负的临时漂移（需 TTL 自愈）。
- 新实现：`_compensate_all` 在 `db.rollback()` 之后读取数据库当前库存并 `SET`（带 TTL）。每个请求退出（成交或失败）都会把闸门校准到权威值，**系统在无进行中请求时必然一致**。
- 实测：订单并发探针结束后 `Redis = 92 = DB = 92`、抢购探针结束后 `Redis = 0 = DB = 0`（改进前为 95 vs 93 的漂移）。残余风险收敛为"进程崩溃瞬间的预扣泄漏"（TTL 兜底）。
- 同步删除死代码 `_redis_compensate`。
